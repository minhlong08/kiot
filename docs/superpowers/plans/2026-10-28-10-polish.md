# Milestone 10 — Polish, Packaging & Data Safety Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Finish the brief: editable print templates with placeholders, keyboard shortcuts, the deferred POS order rules (rounding, require customer), responsive POS at 1366×768 and tablets, production serving of all three web apps from the API, `docker compose up` with Postgres, full backup/restore and reset demo data, and a README that documents running, demo logins and the adapter seams (carrier, messaging, e-invoice).

**Architecture:** Print templates are stored rows (`PrintTemplate { kind, size, body }`) rendered by one shared, dependency-free renderer (`packages/shared/src/template.ts`: `{{field}}`, `{{#lines}}…{{/lines}}`, formatters `{{money total}}`, `{{date createdAt}}`) used by POS receipts and admin prints; seeded defaults reproduce today's layouts. Production: Fastify serves `apps/admin/dist` at `/`, `apps/pos/dist` at `/sale/`, with SPA fallbacks (incl. `/shop`). Postgres: the Prisma schema stays SQLite-first; `scripts/prisma-provider.mjs pg` writes `prisma/pg/schema.prisma` (provider swapped) used by the Docker image with `prisma db push`, and `db.ts` picks `@prisma/adapter-pg` when `DATABASE_URL` starts with `postgres`; the two raw SQL statements become dialect-aware (`MAX(a,b)` → `GREATEST(a,b)`). Backup = a versioned JSON document of every table (provider-agnostic); restore replaces all rows in one transaction and resets sequences.

**Tech Stack:** as before + `@fastify/static`, `@prisma/adapter-pg`, `pg`; Docker (node:24-slim) + postgres:17.

**Spec:** requirements "Tech stack and run requirements", §11, §12; deferred items in docs/superpowers/decisions.md (M6 rounding/require customer, M7 per-group VAT).

## Global Constraints

- All earlier constraints. Template placeholders are escaped HTML by default; `{{{raw}}}` only for store-controlled fields (logo URL, QR data URL). Unknown placeholders render empty, never throw.
- Rounding (`settings.orders.rounding`): `none | hundred | thousand` applied to the invoice total in `computeSale` (nearest; the difference goes to `roundingAdjust`) — the API recomputes, so client and server agree.
- Require customer (`settings.orders.requireCustomer`): POS blocks checkout without a customer; API refuses with `400 CUSTOMER_REQUIRED` (offline-queued sales too).
- Backup: admin only (`isAdmin`), `GET /api/system/backup` streams `{ app, version, createdAt, tables: { Model: rows[] } }`; `POST /api/system/restore` accepts the same (≤ 200 MB), validates `app`/`version`, restores, invalidates all sessions except the caller's. Reset demo: admin only, typed confirmation "XOA DU LIEU", wipes and reseeds.
- Keyboard: admin `F2` new on list pages (when a "+" toolbar action exists), `/` focuses list search, `Esc` closes dialogs (exists); POS keeps F3/F4/F9 and adds `F1` help overlay, `Ctrl+1..9` switch invoice tabs, `F8` print last receipt.

## Review Focus

1. **Restore of a backup taken on another version** → refused with a clear message, nothing changed (Task 5).
2. **Restore partially failing** (bad row) leaves the old data intact (single transaction) (Task 5).
3. **Template with a malicious customer name** (`<script>`) prints escaped (Task 1).
4. **Rounding with exchange credit / points** keeps `due`, `change` and debt consistent between POS and API (Task 2).
5. **Postgres**: `nextCode` and `reserveCode` work concurrently on both dialects (Task 4 test against the SQL builder; Docker smoke in Task 4).
