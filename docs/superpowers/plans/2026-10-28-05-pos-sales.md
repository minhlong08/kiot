# Milestone 5 — POS, Invoices, Returns & Customer Orders Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A keyboard-first cashier app at `/sale` (multi-tab carts, scanner, customer, price books, promotions, vouchers, points, mixed payments incl. VietQR, receipts, fast/normal/delivery modes, offline queue, shifts) backed by authoritative invoice, return/exchange and customer-order services, plus their admin screens.

**Architecture:** One pure function `computeSale()` in `packages/shared` turns a cart into every money figure (line amounts, manual and promotion discounts, voucher, points, rounding, totals, change, debt). The POS calls it for display; the API calls it again inside the invoice transaction and stores *its* result (client figures are never trusted). `createInvoice` is the only writer of invoices and orchestrates the single-writer services: `moveStock`, `postPartnerLedger`, `postLoyalty`, `recordCash`, `redeemVoucher`. Every document status change goes through `transition()` — a conditional `updateMany … where status in (from)` — so double clicks and two tills can never double-post (carried over from the M3 review). Offline: the POS caches its bootstrap data in IndexedDB and queues invoices with a client UUID; the API is idempotent on that UUID.

**Tech Stack:** as M4, plus `idb` (POS IndexedDB), `qrcode` (VietQR image), POS uses React + Tailwind (no router library; screen state in React).

**Spec:** requirements §4 (Hóa đơn, Trả hàng, Đặt hàng), §11 (POS); design §7–8 (money rules, combos, units, VietQR local generation).

## Global Constraints

- All earlier constraints. Prefixes: invoice `HD`, return `TH`, customer order `DH`, invoice payment voucher `TTHD`, return refund voucher `TTTH`, order deposit voucher `TTDH`.
- Invoice statuses: `processing` (Đang xử lý — delivery not finished), `completed`, `undeliverable` (M7), `cancelled`. A non-delivery sale is `completed` immediately.
- Price rules: a line's unit price must equal the price-book (or base/unit) price unless the user has `pos.editPrice`; manual line + invoice discount combined may not exceed the role's `maxDiscountPercent` of the pre-discount amount (`409 DISCOUNT_LIMIT`). Promotion discounts don't count toward that limit.
- Payments: `cash | transfer | card | ewallet | points | deposit`. A walk-in sale (no customer) must be fully paid. With a customer, unpaid remainder becomes debt (refused `DEBT_LIMIT` when `settings.customers.debtLimit > 0` and new debt would exceed it). Overpayment in cash returns change; overpayment in non-cash is refused.
- Rounding (`settings.orders.rounding`) applies to the amount due after all discounts; rounding difference is stored as `roundingAdjust`.
- COGS: each line stores `cost` (per base unit, from `moveStock`'s returned unit cost — combos give the component sum) and invoice `costTotal`.
- Loyalty: earn via `pointsEarned` (M4) on completion only if `settings.customers.loyaltyEnabled` and a customer is set; redeem points as payment `points` at `settings.customers.pointValueVnd`.
- Customer `totalSpent += total − returns`; `lastPurchaseAt`; `autoAssignGroup` after every completion/return.
- Idempotency: `Invoice.clientUuid @unique`; replaying the same uuid returns the existing invoice (200), never a second one.

## Review Focus

1. **Two tills sell the last unit at the same moment** → exactly one succeeds, the other gets `INSUFFICIENT_STOCK` (Task 3 parallel test).
2. **Double click on "Thanh toán" / offline replay** → one invoice (Task 3 idempotency + transition tests).
3. **Return after the price book or promotions changed** → refund uses the invoice's own net line prices, not today's prices (Task 5).
4. **Cancelling an invoice that has returns** → refused `HAS_RETURNS` (Task 3).
5. **POS offline then back online with stock changed meanwhile** → queued invoice syncs if stock allows; otherwise it stays in the queue with the server error shown, and can be edited or discarded (Task 8).

### Task 1: Shared sale math + VietQR

**Files:** `packages/shared/src/sale.ts`, `packages/shared/src/vietqr.ts`, `packages/shared/src/schemas/sales.ts`; tests `packages/shared/test/{sale,vietqr}.test.ts`.

**Produces:**
```ts
type SaleLineInput = { key: string; productId: number; unitId: number | null; conversion: number; groupId: number | null; qty: number; price: number; discount: number /* manual, per line total */; loyaltyEnabled: boolean; fixedPoints: number | null; isGift?: boolean };
type SaleInput = { lines: SaleLineInput[]; invoiceDiscount: number /* manual */; voucherDiscount: number; pointsUsed: number; otherIncome: number; payments: { method: PaymentMethod; amount: number }[]; hasCustomer: boolean };
type SaleContext = { promotions: Promotion[]; promoCtx: PromoContext; pointValueVnd: number; vndPerPoint: number; rounding: 'none'|'hundred'|'thousand'; loyaltyEnabled: boolean };
type SaleResult = {
  lines: (SaleLineInput & { promoDiscount: number; amount: number /* qty*price - discount - promoDiscount */ })[];
  gifts: { productId: number; qty: number; promotionId: number }[]; applied: PromoResult['applied'];
  subtotal: number /* Σ line amounts */; promoInvoiceDiscount: number; invoiceDiscount: number; voucherDiscount: number;
  pointsValue: number; otherIncome: number; roundingAdjust: number; total: number /* khách cần trả, before points */;
  due: number /* total − pointsValue */; paid: number /* Σ non-points payments */; change: number; debt: number; pointsEarned: number;
};
computeSale(input: SaleInput, ctx: SaleContext): SaleResult
discountLimitExceeded(result: SaleResult, maxPercent: number): boolean // manual (line + invoice) vs Σ qty*price
```
`total = round(subtotal − promoInvoiceDiscount − invoiceDiscount − voucherDiscount + otherIncome)`; `due = total − pointsValue`; `change = max(0, paid − due)` (cash only); `debt = max(0, due − paid)`.
- `buildVietQrPayload({ bankBin, accountNumber, amount, description }): string` (EMVCo: 00/01/38 with GUID `A000000727`, 53=704, 54 amount, 58=VN, 62.08 description, 63 CRC16-CCITT-FALSE uppercase hex) and `crc16ccitt(s)`.
- `invoiceInputSchema` (lines, customerId?, priceBookId?, sellerId?, channel, invoiceDiscount, voucherCode?, pointsUsed, otherIncome, payments[{method, amount, fundId?}], note, clientUuid?, createdAtClient?, delivery?: { receiverName, receiverPhone, address, partnerId?, fee, cod, weight, note }, orderId?).

- [ ] **Failing tests:** line amounts with manual + promo discount; invoice tier promo after line discount; voucher + points + other income; rounding to thousand (`1,234,567 → 1,235,000`, roundingAdjust 433); change for cash overpay; debt with customer; points earned on paid part; `discountLimitExceeded` at 10%; gift lines priced 0; VietQR CRC of a known payload (`crc16ccitt('123456789') = '29B1'`) and payload contains `5303704`, `5802VN`, amount field `54071500000`.

### Task 5: Returns & exchange

`createReturn(tx, ctx, input)` — from invoice: per line `qty ≤ sold − returned` (`RETURN_EXCEEDS_SALE`), refund price = the line's net unit price after line, promo and allocated invoice-level discounts (`netUnitPrice` helper in shared), stock back via `moveStock(+, unitCost = line.cost)`; quick return (no invoice): price entered, stock back at current cost. `returnFee` deducted. Refund: cash/transfer voucher out `TTTH` and/or `debt` (reduces customer debt). Points reversed `floor(invoice.pointsEarned × total / invoice.total)`; customer `totalSpent −= total`. Exchange: `{ ...returnInput, exchange: invoiceInput }` creates the return then a new invoice in the same transaction; the refund amount is applied as an `exchange` payment on the new invoice (difference paid or refunded). Cancel return reverses. API `/api/returns` list/detail/create/cancel/export.
- [ ] Tests: `refund uses invoice net prices after price change`, `partial returns cap`, `refund to debt`, `points reversed proportionally`, `exchange nets the difference`, `cancel return restores`.
